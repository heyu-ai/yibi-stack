# Explain to PM

把一個技術議題整理成一頁**給 PM 看的圖文 HTML**。

主題來自使用者在指令後附的參數，可以是：

- PR：優先接受 PR URL 或 `owner/repo#123`；也接受 `#123` 或 `123`
- 檔案路徑（ADR、design.md、spec）
- 一段描述
- 留空：以目前對話中最近一個待決策的技術議題為主題；判斷不出來就先問一句「要解釋哪一件事」

讀者是 PM：懂產品、懂使用者、懂時程與成本，**不看 code**。這頁的目標是讓 PM 讀完 3 分鐘內能回答：
「發生什麼事？對使用者、時程、成本有什麼影響？我要決定什麼？選哪個？」

## Step 1｜蒐集事實（先查證，再解釋）

### 解析 PR 參數

1. 去掉參數開頭的 `#`。不去掉的話，shell 會把 `#123` 之後的內容全部當成註解，`gh` 只會看到
   `gh pr view`，改抓目前 branch 的 PR。
2. 決定 repo：
   - 參數是 URL 或 `owner/repo#n`：用其中的 `owner/repo`。
   - 參數只有數字：用目前目錄所在 repo，並在頁面出處區與回覆中寫出實際的 `owner/repo` 與 PR 標題，
     讓使用者確認抓到的是他要的那個 PR。
3. 之後每個 `gh` 呼叫都帶 `--repo <owner/repo>`，不要依賴目前目錄。

### 取得資料

| 參數 | 取得方式 |
|------|---------|
| PR | `gh pr view <n> --repo <owner/repo> --json title,body,files,additions,deletions,reviews,comments`、`gh pr diff <n> --repo <owner/repo>` |
| PR 的 review 結果 | 另抓 inline review comment：`gh api repos/<owner>/<repo>/pulls/<n>/comments`（`gh pr view` 的 `reviews,comments` 不含 inline 留言） |
| 檔案路徑 | Read 全文；有引用其他檔就一併讀 |
| 描述或對話脈絡 | 用對話內容；提到的檔案、issue、PR 都實際去讀 |

規則：

- 每個寫進頁面的事實都要有出處（檔案、PR、issue、量測結果）。查不到就標「推論」，不要寫成定論。
- 區分**實測**（跑過、量過）與**推論**（依經驗判斷），頁面上用不同標籤呈現。
- **主要來源**（使用者指定的 PR、檔案）的任一個 `gh` 呼叫或讀取失敗時，印出
  `[FAIL] <來源> 讀取失敗：<錯誤>` 並停止，不要憑記憶補內容。
- **次要來源**（主要來源裡引用的其他檔案或連結）讀不到時，在「給工程師的出處」標成「未取得」後繼續，
  並在回覆中列出。

## Step 2｜判斷頁面類型

- **A. 解釋型**：已經決定或已經做完，只需要讓 PM 理解（例如「這個 PR 改了什麼、對使用者有什麼差別」）。
- **B. 決策型**：資料裡有兩個以上可行方向，且還沒有定案，需要 PM 或 owner 拍板。

判斷不出來時，先問使用者一句「這件事已經定案，還是需要 PM 決定？」。無法詢問時當成 A 型，
並在頁首標明「頁面類型為推論」。不要為了湊出選項而自己編替代方案。

## Step 3｜寫頁面內容

### 白話規則（每一句都要符合）

1. **用影響說話，不用實作說話**：寫「家長按下播放後要多等 3 秒」，不寫「API latency 增加」。
2. **技術名詞第一次出現就翻譯**，並放進頁尾「名詞小抄」。能不用就不用。
3. **每個抽象概念配一個生活類比**（例：快取＝把常用的書放在桌上，不用每次去書庫拿）。類比要註明哪裡不像，避免誤導。
4. **數字要具體**：時間、人天、金額、影響多少使用者。不確定就給範圍，並說明怎麼估的。
5. 結論放第一句；一句只講一件事；不用箭頭鏈代替句子。
6. 正文不放 code、檔案路徑、函式名；需要追溯的出處放在頁尾「給工程師的出處」折疊區。

### 頁面結構（依序）

1. **一句話結論**（頁首大字）：A 型寫「這件事是什麼、影響是什麼」；B 型寫「需要你決定 X，我們建議 Y」。
2. **為什麼要在意**：對使用者、時程、成本、風險各一行；沒有影響的面向寫「無影響」，不要省略。
3. **用一個例子講背景**：以一位具體使用者（例如「媽媽小美晚上 9 點要讓孩子聽睡前故事」）走一遍情境，
   對照「現在」與「改了之後」（或各選項之下）會發生什麼。
4. **圖解**（至少一張，最多四張，inline SVG），依內容挑最適合的形式：
   - 流程圖：使用者操作或系統步驟的先後順序
   - 前後對照：現在與改了之後，左右並排
   - 時間軸：時程、分階段上線
   - 比較圖：各選項在成本、時間、風險上的相對大小

   每張圖下方用一句話說明「這張圖要看什麼」。圖只畫真實機制，不畫裝飾。
5. **選項**（僅 B 型）：2–4 個，每個一張卡片，包含：
   - 一句話說明這個選項是什麼
   - 使用者會感受到什麼
   - 優點與缺點（各 2–4 點，白話）
   - 成本與時程估計，以及估計依據（實測或推論標籤直接標在卡片上）
   - 風險，以及「什麼情況下會後悔選這個」

   卡片之後放一張**比較表**：列為選項，欄為使用者體驗、開發時間、成本、風險、日後改變的難度，
   用「高／中／低」或具體數字。
6. **我們的推薦**（僅 B 型）：
   - 推薦哪個，理由 2–3 點
   - **取捨**：選它等於放棄了什麼，明白寫出來
   - 哪些條件改變時應該改選別的（例如「若上線日期提前到 12 月，改選 B」）
   - 涉及架構裁決時，明寫「這是建議，最後由你或 owner 決定」，不要寫成已經決定
7. **需要你回覆什麼**：列出要 PM 回答的問題，每題附預設答案（PM 不回覆時我們會怎麼做）與期限（若有）。
8. **名詞小抄**：頁面用到的每個技術詞，一行白話定義。
9. **給工程師的出處**（`<details>` 折疊）：repo 與 PR 標題、檔案路徑、issue、量測指令與結果，並標示實測、推論或未取得。

A 型省略第 5、6 節；第 7 節沒有要問的事就寫「不需要你做任何事，僅供知悉」。

## Step 4｜產出 HTML

警告：發布會把內容送到外部服務。先完成第 1 點的敏感內容確認，再進行後面的步驟。

1. **敏感內容確認**：檢查整頁內容（含折疊的出處區）。以下是不得發布的內容，清單**不是**窮盡的，
   拿不準時一律當成敏感：
   - 憑證、API key、token、密碼、私鑰
   - 內部網址、IP、主機名稱
   - 未修補的安全弱點細節
   - 客戶或使用者的個人資料
   - 未公開的營收、人事資訊

   含有這類內容時，先從頁面刪除；刪除後仍無法呈現主題時，改為**不發布**，只交付本機檔案。
2. **決定頁面形式**：有 Artifact tool 時，先依該工具的說明呼叫 `action: "quickstart"`（`intent: "other"`），
   依回傳結果決定用哪種類型與要先載入哪些 skill（例如 `artifact-design`）。
   - quickstart 指示的 skill 不存在或載入失敗時，印 `[WARN] <skill> 不可用，依本節第 4 點的版面要求直接撰寫`，
     繼續執行，並在回覆中列出。
   - `dataviz`、`artifact-diagramming` 只在可用時載入；不可用時同樣印 `[WARN]` 後繼續。
3. 目前 repo 有設計系統文件時可借用其色彩，但這是內部說明頁，不要做成產品畫面。
4. 寫成單一 `.html`（inline CSS 與 SVG，不載入外部圖片）。版面要求：手機寬度可讀、支援深色模式、
   選項卡片在窄螢幕改為直排、比較表在窄螢幕不破版。
5. 用 Write tool 寫檔（同日同主題重跑時直接覆寫；不要用 shell `>` 重導向，zsh `noclobber` 下會靜默保留舊檔）：
   - 有 `$CLAUDE_JOB_DIR` 時：`$CLAUDE_JOB_DIR/tmp/explain-to-pm-<YYYY-MM-DD>-<slug>.html`
   - 沒有時：session 有系統提供的 scratchpad 目錄就用它，否則用 `/tmp/explain-to-pm-<YYYY-MM-DD>-<slug>.html`。
     不要在 repo 內建立新目錄。

   寫檔失敗時印 `[FAIL] 寫入 <路徑> 失敗：<錯誤>` 並停止。
6. **發布**（有 Artifact tool，且第 1 點沒有判定為不發布時）：發布成私人頁面，把連結給使用者轉給 PM。
   - 發布失敗時印 `[FAIL] Artifact 發布失敗：<錯誤>`，改交本機檔案路徑。
   - 沒有 Artifact tool 時，交付本機檔案路徑。
   - 只回報工具結果中實際取得的連結，不要自己組 URL。

## Step 5｜交付前自我確認

逐項確認，任何一項不符就回頭改：

- [ ] 第一句就是結論，PM 不必讀完全文才知道要做什麼
- [ ] 正文沒有未翻譯的技術名詞、檔案路徑、函式名
- [ ] 每個抽象概念都有例子或類比
- [ ] 至少一張圖，且每張圖都有一句「看什麼」的說明
- [ ] （B 型）每個選項都有優點、缺點、成本、風險；推薦段寫出了放棄什麼
- [ ] 正文每個估計數字與選項旁都有實測或推論標籤，不只標在出處區
- [ ] 每個事實都能在「給工程師的出處」找到來源
- [ ] 「需要你回覆什麼」每題都有預設答案
- [ ] 頁面（含折疊區）不含 Step 4 第 1 點列的敏感內容；含有時已改為不發布

## 回覆使用者

回覆以下各項，不要把頁面內容貼回對話：

1. 頁面連結或檔案路徑，以及實際解釋的對象（例如 `owner/repo#123 <PR 標題>`）
2. 一句話結論
3. （B 型）推薦選項，以及最需要 PM 回答的那一題
4. 有以下任一情況時必列，一項一行：沒有發布與原因、發布失敗、`[WARN]` 略過的 skill、標成「未取得」的次要來源
